OAuth2 Authentication

This add-on adds a new authentication method which obtains an OAuth2 access token directly from a token endpoint, without using a browser. It supports the following non-interactive grant types:
  • client_credentials
  • password (Resource Owner Password Credentials)

The Client ID, Client Secret, Grant Type and Token Endpoint are configured on the authentication method itself (they are typically shared by all of the users of a context). The following are configured per user, via the user's credentials, as applicable to the configured grant type:

  • username and password - required for the password grant type
No per-user credentials are required for the client_credentials grant type.

Refresh Tokens

If the token endpoint returns a refresh_token alongside the access token, it is captured and stored automatically - there is no user configuration for it. On the next authentication attempt for that user, ZAP tries a refresh_token grant first using the stored value (falling back to the configured grant type, e.g. password, if it's rejected), and keeps the stored value up to date, so IdPs that rotate refresh tokens on every use are handled transparently.

Client Authentication

The Client Authentication Method controls how the Client ID and Client Secret are sent to the token endpoint:
ValueDescription
client_secret_basicClient ID and Secret are sent using HTTP Basic Authentication. This is the default.
client_secret_postClient ID and Secret are sent as parameters in the request body.
noneOnly the Client ID is sent, in the request body - for public clients that do not have a secret.

Session Identification

The token endpoint's JSON response is passed to the configured Session Management Method, so the access and refresh tokens are always available for use in Header Based Session Management placeholders as {%json:access_token%} and {%json:refresh_token%} - this is the case even if the IdP's token endpoint uses different field names, as long as the Access Token Field / Refresh Token Field parameters are configured accordingly, since they are copied to the standard access_token / refresh_token JSON keys before being handed off to session management.

Session Management / Verification Autodetection

If Session Management and/or Authentication Verification are explicitly set to autodetect, they are resolved automatically as soon as authentication succeeds, without needing any traffic beyond the token request itself (they do not default to autodetect if simply left unconfigured - the Automation Framework's own defaults apply in that case, as for any other method). Session Management is always set to Header Based, using Authorization: Bearer {%json:access_token%}. Verification depends on whether verificationUrl is configured:
  • Not set (default): response-based checking of the HTTP status line - 200 OK means logged in, 401 Unauthorized means logged out (the RFC 6750 convention for a bearer-token-protected resource rejecting a missing/invalid/expired token). This is a reasonable default but says nothing about the specific target application.
  • Set to an RFC 7662 OAuth 2.0 Token Introspection endpoint: ZAP polls it - authenticating as the OAuth2 client, the same way as at the token endpoint, POSTing token=<current access token> - and checks the standard active field instead. This is a precise, purpose-built signal that doesn't depend on the target application's own conventions at all, and is the recommended option whenever the IdP exposes an introspection endpoint.
This is all done directly by the authentication method itself, since - unlike browser-driven methods - it already knows exactly what its own token/introspection responses look like; the generic autodetection mechanism (which watches proxied/spidered traffic for session tokens being reused) doesn't apply here, as there's no such follow-up traffic for it to observe.

Diagnostics

Ticking "Record Diagnostics" on the authentication method records the token request/response for each authentication attempt, viewable afterwards via the add-on's Diagnostics panel - useful for troubleshooting a failing token exchange.

Automation Framework

OAuth2 Authentication can be configured in the environment section of an Automation Framework plan using: 
      authentication:
        method: "oauth2"
        parameters:
          grantType:                   # String, one of: client_credentials, password. Default: client_credentials
          tokenEndpoint:               # String, the URL of the token endpoint, mandatory
          clientId:                    # String, the OAuth2 Client ID
          clientSecret:                # String, the OAuth2 Client Secret
          clientAuthMethod:            # String, one of: client_secret_basic, client_secret_post, none. Default: client_secret_basic
          scope:                       # String, the OAuth2 scope(s) to request
          accessTokenField:            # String, the JSON field name of the access token in the token response. Default: access_token
          refreshTokenField:           # String, the JSON field name of the refresh token in the token response. Default: refresh_token
          extraTokenParams:            # Map, extra parameters to send in the token request, e.g. { audience: "https://api.example.com" }
          diagnostics:                 # Boolean, record diagnostics for troubleshooting. Default: false
          verificationUrl:             # String, an RFC 7662 introspection endpoint, for autodetected Verification (see below)
      sessionManagement:
        method: "headers"
        parameters:
          Authorization: "Bearer {%json:access_token%}"

Credentials for the password grant type are defined as usual under the user credentials, for example: 

      credentials:
        username: …
        password: …
