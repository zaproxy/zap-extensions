Mock OAuth2 Authorization Server

A mock OAuth2 Authorization Server (and a demo relying-party app), supporting all four grant types (client_credentials, password, refresh_token and authorization_code with PKCE), for testing the authhelper add-on's direct/non-interactive OAuth2 authentication method (client_credentials/password, with refresh_token handled automatically).

authorization_code is inherently a browser-redirect flow, so it isn't exercised by that method - try the demo app to drive it manually in a real browser, independently of ZAP, or use ZAP's Browser-Based/Client Script Based Authentication against it.

Endpoints

  • Authorization Endpoint: https://authserver.oauth2.zap/authorize
  • Token Endpoint: https://authserver.oauth2.zap/token
  • Introspection Endpoint (RFC 7662, for verification): https://authserver.oauth2.zap/introspect (client-authenticated the same way as the Token Endpoint; POST token=<value>, returns {"active": true|false, ...})
  • Protected resource (for verification/poll URL testing): https://api.oauth2.zap/userinfo (expects Authorization: Bearer <token>)

Test clients

  • Confidential client (use with client_secret_basic or client_secret_post): client_id=test-client, client_secret=test-secret
  • Public client (use with client_auth_method: none, typically with PKCE): client_id=test-public-client, no secret

Test user

  • username = test@test.com
  • password = password123

Testing non-standard token field names

Add field_style: custom to the token request (e.g. via extraTokenParams) to have the token endpoint return accessToken/refreshToken instead of the standard access_token/refresh_token - useful for testing the accessTokenField/refreshTokenField normalization.

Example ZAP Automation Framework configuration

client_credentials

authentication:
  method: "oauth2"
  parameters:
    grantType: "client_credentials"
    tokenEndpoint: "https://authserver.oauth2.zap/token"
    clientId: "test-client"
    clientSecret: "test-secret"
sessionManagement:
  method: "headers"
  parameters:
    Authorization: "Bearer {%json:access_token%}"

password

authentication:
  method: "oauth2"
  parameters:
    grantType: "password"
    tokenEndpoint: "https://authserver.oauth2.zap/token"
    clientId: "test-client"
    clientSecret: "test-secret"
sessionManagement:
  method: "headers"
  parameters:
    Authorization: "Bearer {%json:access_token%}"
users:
- name: "Test User"
  credentials:
    username: "test@test.com"
    password: "password123"

refresh_token

Not user-configurable - the authhelper add-on's OAuth2 method captures the refresh_token returned by the password example above automatically (the mock server's client_credentials grant deliberately does not issue one, matching common IdP practice), and reuses it on subsequent authentications without needing a refresh_token grantType or a refreshToken credential. This mock server rotates the refresh token on every use (an old, already-used token is rejected with invalid_grant), so it can be used to exercise that behaviour end-to-end.

Verification

Session Management and Verification must both be explicitly set to autodetect for ZAP to resolve them automatically (they don't default to it if omitted): Session Management becomes Header Based (Authorization: Bearer {%json:access_token%}), and Verification becomes response-based checking of the HTTP status line (200 OK vs 401 Unauthorized) by default. For a more precise, target-independent signal, set verificationUrl to https://authserver.oauth2.zap/introspect: ZAP polls it with the current access token and checks the standard active field instead, which this mock server implements per RFC 7662, e.g.: 

authentication:
  method: "oauth2"
  parameters:
    grantType: "password"
    tokenEndpoint: "https://authserver.oauth2.zap/token"
    clientId: "test-client"
    clientSecret: "test-secret"
    verificationUrl: "https://authserver.oauth2.zap/introspect"
  verification:
    method: "autodetect"
sessionManagement:
  method: "autodetect"
users:
- name: "Test User"
  credentials:
    username: "test@test.com"
    password: "password123"

authorization_code (with PKCE)

There is no Automation Framework authentication method for driving this flow directly - it requires a real browser redirect to the /authorize endpoint and its login/consent page, which is what the demo app is for (manually, independently of ZAP). To exercise it under ZAP/the Automation Framework instead, use Browser-Based Authentication or Client Script Based Authentication configured to drive a real browser to https://app.oauth2.zap/ and click through the login form.
