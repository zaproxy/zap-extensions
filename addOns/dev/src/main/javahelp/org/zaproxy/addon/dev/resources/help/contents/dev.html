Dev Add-On

An add-on to help with development of ZAP. It starts a simple test web service, which by default will be accessible via http://localhost:9091

It provides:

API Pages

Two simple OpenAPI specs, both of which require no authentication. One of the APIs described by the specs can only be accessed when authenticated.

Authentication Pages

A growing set of authentication pages, for use in testing ZAP authentication handling.

CSRF Pages

A set of pages with forms and CSRF tokens that are checked on POST requests.

HTML Pages

A set of pages which store various types of data in localStorage and sessionStorage.

Full Apps

A set of more complete apps for testing ZAP functionality end-to-end.

Random Pages

Dynamically generated sites for testing scalability.

Sequence Pages

A set of pages for testing the sequence add-on.

Adding Your Own Test Apps

Other add-ons can plug their own test apps into the server, so that they can live with the add-on they test. The add-on must depend on the dev add-on and, in its extension's optionsLoaded() (the server is created when the dev add-on is hooked), call: 
Control.getSingleton().getExtensionLoader().getExtension(ExtensionDev.class)
        .getTestServer()
        .ifPresent(server -> server.addDirectory("auth", new MyAppDir(server, "my-app")));
The test server only exists when ZAP is run in dev mode, so nothing should be done if it is not present.

Any missing parent directories are created, and the app is then available under /auth/my-app/. Its static files are read from addOnData/dev/auth/my-app in the ZAP home directory, which the add-on can populate by including them under zapHomeFiles/addOnData/dev/auth/my-app. The add-on should call removeDirectory("auth/my-app") when it is unloaded.

Directories plugged in have their state reset, like all the other test apps, when ZAP's session changes.

Test Add-Ons

Test apps should live in a test add-on next to the add-on they test, not in the dev add-on. To create one, add the directory <id>Test inside the directory of the add-on to test, for example addOns/llm/llmTest, and put the src, a CHANGELOG.md and a an empty <id>Test.gradle.ktslt;idan empty <id>Test.gradle.ktsgt;Test.gradle.kts with just a comment in it. No other build configuration is needed, the build finds it and configures it from the add-on being tested and the dev add-on:
  • it has the version 0.0.1, the alpha status and a name and description based on the add-on being tested;
  • it depends on the dev add-on and the add-on being tested, in the manifest and for compiling, as well as the add-ons they depend on.
If it needs anything else, for example another test add-on, add it to the <id>Test.gradle.kts file, which can use the usual zapAddOn dependencies and manifest settings, and can override the defaults.

Test add-ons are not translated. The LLM test add-on (addOns/llm/llmTest) is the reference example. It provides a mock OpenAI compatible LLM at /llm/mock/v1, which other test add-ons can extend with their own rule sets, see its README.md. Build one with ./gradlew :addOns:llm:llmTest:jarZapAddOn or install it with cZAO, and run ZAP with -dev.
